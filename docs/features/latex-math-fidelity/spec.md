# Математика в тесте: всё, что не чисто текст, идёт в vision; LaTeX в промпте

## Problem

Математика из PDF теряется или искажается ещё на этапе извлечения текста, и в
сгенерированном тесте появляются математически неверные задания. Проверка на
реальном `ma_9_oge_2026_demo-5_cropped.pdf` (лежит в корне репозитория)
показала, что локальное извлечение текстового слоя корректно только для задания
6; в остальных местах:

- знак корня молча теряется: `1/(2+√3) + 1/(2−√3)` превращается в `1/(2+3)...` —
  выражение становится другим, а не просто некрасивым;
- уравнение разваливается: `2 2 3 1 0 x x − +=` вместо `2x² − 3x + 1 = 0`;
- порядок вариантов ответа перепутан (13/9 оказывается не на своём месте);
- остаётся мусор от служебных глифов.

Ранее (approved-версия этого спека и PR #5) ставка была на локальную эвристику
восстановления дробей по векторной черте. Она недостаточна: корни, порядок
строк и многоэтажные выражения она не лечит, информация отсутствует в текстовом
слое. Решение CEO: не чинить локальное извлечение, а отдавать во vision всё, что
не является чисто текстовым.

## Current behavior

`backend/app/text_extract.py`, `_from_pdf`:

1. `pymupdf4llm.to_markdown` даёт Markdown по страницам.
2. Для страниц, где `page_has_symbol_font(page)` (`text_clean.py`) — True, текст
   собирается локально: `clean_markdown(page_text_from_dict(page))` (ремап
   Symbol-глифов, индексы). Остальные — из `pymupdf4llm`.
3. `_page_needs_vision(page, md_text)`: `vision_enabled` И (`len(text.strip()) <
   vision_min_text_chars` (200) ИЛИ `page.get_images()` не пуст). Векторные
   рисунки и Symbol-шрифт в условие не входят — математическая страница с
   текстом >= 200 символов и без растровых картинок остаётся на локальном пути.
4. Страницы, выбранные для vision (не более `vision_max_pages`=20, в порядке
   страниц), рендерятся в PNG и распознаются `transcribe_page` (`llm.py`) с
   `VISION_SYSTEM_PROMPT`, уже требующим LaTeX. `transcribe_page` при сбое
   возвращает `""`, и тогда остаётся ранее собранный локальный текст страницы.

В ветке `feature/latex-math-fidelity` (PR #5) поверх этого добавлено
(относительно `main`):
- `backend/app/text_clean.py`: `_find_fractions` и связанный код
  восстановления дробей внутри `page_text_from_dict` (~110 строк);
- `backend/tests/test_text_clean.py`: тесты этой эвристики;
- `backend/app/llm.py`: LaTeX-инструкция в `SYSTEM_PROMPT` (остаётся).

## Solution

### 1. Маршрутизация: локальный путь только для чисто текстовых страниц

PDF-страница остаётся на локальном текстовом пути тогда и только тогда, когда
выполнены ВСЕ условия:

- `page_has_symbol_font(page)` — False (нет Symbol/математического шрифта);
- `page.get_images()` пуст (нет растровых картинок);
- `page.get_drawings()` пуст (нет векторной графики);
- `len(text.strip()) >= settings.vision_min_text_chars`, где `text` —
  очищенный локальный текст страницы (как сегодня).

Любая другая страница ("не чисто текстовая") при `vision_enabled=True` идёт в
vision. Предикат `_page_needs_vision` — это отрицание "чисто текстовой":

```
needs_vision = vision_enabled and (
    len(text.strip()) < vision_min_text_chars
    or bool(page.get_images())
    or page_has_symbol_font(page)
    or bool(page.get_drawings())
)
```

Принятое следствие: страницы с линиями таблиц, подчёркиваниями, рамками или
колонтитулами-линейками (это векторные рисунки) тоже уйдут в vision. Это
осознанная цена простоты правила; расход ограничен `vision_max_pages` (20).

Не меняется: `vision_max_pages`, порядок отбора (по порядку страниц),
`vision_concurrency`, `vision_dpi`. Новых настроек нет.

### 2. Поведение без vision и при сбое: обычный локальный текст

Если `vision_enabled=False`, если `transcribe_page` вернул пустую строку/упал,
либо страница не влезла в `vision_max_pages` — страница остаётся с локальным
текстом, который собирался и до этого изменения: для Symbol-страниц
`clean_markdown(page_text_from_dict(page))` (ремап Symbol-глифов и индексы, как
на `main`), для остальных — Markdown из `pymupdf4llm`. Никакой реконструкции
дробей или иной "умной" математической логики в этом fallback'е нет. Качество
математики в нём — как было до PR #5; это известное ограничение.

### 3. Локальная эвристика дробей удаляется

Код PR #5 удаляется: `_find_fractions` и всё, что она добавила в
`page_text_from_dict` (пометки `_anchor`/`_fracs`, потребление span'ов и т.п.),
а также её тесты в `backend/tests/test_text_clean.py`. `text_clean.py` и
`test_text_clean.py` возвращаются к поведению `main` (кроме случаев, когда там
после PR #5 появилось что-то не связанное с дробями — такого в диффе не
обнаружено). `page_has_symbol_font` остаётся и используется в маршрутизации.
Локальная логика (`page_text_from_dict` для Symbol-fallback, `clean_markdown`,
`pymupdf4llm`) сохраняется для docx/txt/md и для чисто текстовых PDF-страниц.

### 4. Промпты

Инструкция про LaTeX в `SYSTEM_PROMPT` (`llm.py`) остаётся как есть.
`VISION_SYSTEM_PROMPT` уже требует LaTeX; правится только если проверка на
демо-PDF покажет, что модель теряет корни/порядок вариантов из-за формулировки
— решение backend-dev по результату проверки, фиксируется в PR.

## User stories / flow

1. Пользователь загружает `ma_9_oge_2026_demo-5_cropped.pdf` при включённом
   vision. Все страницы, содержащие Symbol-шрифт, картинки или векторные
   рисунки, уходят в vision; в контексте `1/(2+√3)+1/(2−√3)` записано как
   `\frac{1}{2+\sqrt{3}}+\frac{1}{2-\sqrt{3}}` внутри `$...$`, уравнение как
   `2x^2 - 3x + 1 = 0`, варианты ответа — в исходном порядке.
2. Модель генерации составляет вопросы по контексту и по инструкции пишет
   математику в LaTeX; фронтенд рендерит её через существующий KaTeX
   (`RichText.tsx`) без изменений.
3. Пользователь загружает чисто текстовый PDF (без Symbol, картинок и рисунков,
   с достаточным количеством текста) — vision не вызывается, как сегодня.
4. Если vision выключен или упал на странице — используется обычный локальный
   текст этой страницы без каких-либо попыток восстановить формулы.

## Out of scope

- Любое улучшение локального извлечения математики (дроби, корни, порядок
  вариантов) — локальная эвристика дробей полностью удаляется, а не сохраняется
  как fallback.
- Приоритизация страниц внутри `vision_max_pages`, новые настройки/флаги,
  настраиваемые пороги; различение "настоящей" графики и линий таблицы/рамки.
- Изменения фронтенда, API-контракта и pydantic-схем.
- Vision для DOCX/TXT/MD: они остаются на локальном пути.
- Инвалидация дискового кэша извлечения (`ingest_cache_dir`, ключ — SHA-256
  файла): старые результаты остаются; для проверки нужен "холодный" прогон.

## Acceptance criteria

- [ ] `_page_needs_vision` при `vision_enabled=True` возвращает True, если
      выполнено хотя бы одно: текст короче `vision_min_text_chars`; есть
      растровые изображения; есть Symbol-шрифт; `get_drawings()` непуст.
      Возвращает False только для страницы, у которой нет ничего из этого.
      При `vision_enabled=False` всегда False.
- [ ] Юнит-тесты `_page_needs_vision` покрывают: чисто текстовая страница
      (False), страница с картинкой, с Symbol-шрифтом, с векторными рисунками,
      с коротким текстом (True), `vision_enabled=False` (False).
- [ ] Если vision вернул пустую строку/упал для страницы, результат содержит
      обычный локальный текст страницы (не пустую страницу); тест с замоканным
      `transcribe_page`.
- [ ] `_find_fractions` и весь связанный с дробями код удалены из
      `text_clean.py`; тесты дробей удалены из `test_text_clean.py`; остальные
      тесты `text_clean` проходят без изменений; `page_has_symbol_font`
      сохранён.
- [ ] `SYSTEM_PROMPT` по-прежнему требует LaTeX для математики.
- [ ] docx/txt/md извлекаются как раньше (нет регрессии).
- [ ] Ручная проверка на `ma_9_oge_2026_demo-5_cropped.pdf` (холодный прогон,
      vision включён, реальная модель), результат приложен к PR:
      - знак корня сохранён: `\sqrt{3}` присутствует в выражении
        `1/(2+√3)+1/(2−√3)`, а не `2+3`;
      - уравнение распознано корректно (`2x^2 - 3x + 1 = 0` или эквивалент), без
        склейки вида `2 2 3 1 0 x x − +=`;
      - варианты ответа (включая 13/9) идут в исходном порядке и в нужных местах;
      - задание 6 (`1/(1/30+1/42)`) корректно.
- [ ] Автотесты не ходят в реальный vision (мок `transcribe_page`);
      `uv run ruff check .` и `uv run pytest -q` чистые.
