# Дроби и формулы рендерятся, а не плоской строкой

## Problem

В сгенерированном тесте математические выражения с дробями отображаются как
плоская строка вида `1/(1/15+1/25)` вместо визуальной дроби с горизонтальной
чертой, хотя фронтенд уже умеет рендерить формулы через KaTeX.

## Current behavior

Фронтенд не виноват: `frontend/src/components/RichText.tsx` уже корректно
рендерит через KaTeX любой текст, обрамлённый `$...$`, `$$...$$`, `\(...\)`,
`\[...\]` — если фрагмент не обрамлён одним из этих разделителей, он рендерится
как обычный текст (это ожидаемое поведение, не баг). Проблема — в том, что
математика до фронтенда доходит без LaTeX-разметки. Два независимых источника:

1. **Промпт генерации теста не просит LaTeX.** `SYSTEM_PROMPT` и
   `build_user_prompt` (`backend/app/llm.py`) не содержат ни слова про формат
   математики. Даже если исходный контекст уже содержит корректный LaTeX
   (например, от vision-распознавания), генерирующая модель не обязана сохранять
   этот формат для собственного текста вопроса/варианта/объяснения.
2. **Текстовый (не-vision) путь извлечения не восстанавливает дроби.**
   Страницы с математикой, набранной шрифтом Symbol, но с достаточным
   количеством текста, не уходят в vision (`_page_needs_vision` в
   `text_extract.py` смотрит только на объём текста и наличие растровых
   изображений — векторные линии в счёт не идут), а обрабатываются
   `page_text_from_dict`/`clean_markdown` (`text_clean.py`). Этот путь построчно
   склеивает текстовые span'ы слева направо, с ремапом Symbol-глифов и
   обозначением над/подстрочных индексов (`^()`, `_()`) — но **не имеет** никакой
   логики для дробей: горизонтальная черта дроби в PDF — это векторная линия,
   а не текст, поэтому числитель и знаменатель просто становятся двумя
   несвязанными строками текста без указания, что это дробь. Даже
   `VISION_SYSTEM_PROMPT`, который просит LaTeX (`$...$`/`$$...$$`), в этом пути
   не участвует — эти страницы вообще не попадают в vision.

Только страницы, реально прошедшие через vision-распознавание, сегодня получают
корректный LaTeX для формул (включая дроби). Страницы с математикой, набранной
Symbol-шрифтом, но признанные "достаточно текстовыми" (нет картинок, много
текста), — не получают LaTeX вообще, независимо от промпта генерации.

## Solution

Обе причины устраняются, в соответствии с решением CEO.

### 1. Промпт генерации инструктирует про LaTeX

`SYSTEM_PROMPT` (`backend/app/llm.py`) дополняется инструкцией:

> Записывай все математические выражения (дроби, степени, корни, формулы) в
> LaTeX: `$...$` для строчных выражений, `$$...$$` для выключных. Дроби — только
> через `\frac{числитель}{знаменатель}`, не как `a/b`.

Это гарантирует, что даже вновь придуманные моделью числа/выражения (а не
дословно перенесённые из источника) выходят в формате, который фронтенд уже
умеет рендерить.

### 2. Восстановление дробей в текстовом пути извлечения (`text_clean.py`)

`page_text_from_dict` дополняется эвристикой распознавания дроби по векторной
черте:

- Через `page.get_drawings()` находятся короткие горизонтальные векторные линии
  (высота bbox ≈ 0, разумная ширина) — кандидаты в черту дроби.
- Для каждой такой линии собираются текстовые span'ы, чьи bbox лежат строго над
  ней (числитель) и строго под ней (знаменатель), в пределах её горизонтального
  диапазона.
- Если и числитель, и знаменатель однозначно определяются (ровно одна группа
  span'ов сверху и снизу, без пересечения с другими чертами дроби на той же
  строке) — они заменяются на `\frac{<числитель>}{<знаменатель>}`, обёрнутое в
  `$...$`, и вставляются в текст на месте черты; span'ы, ставшие числителем и
  знаменателем, не дублируются как отдельный текст строки.
- Если разбить однозначно не получается (черта дроби есть, но группировка
  спорная — например, несколько черт близко друг к другу, вложенные дроби с
  более чем одним уровнем) — эвристика не применяется, страница остаётся с
  текущим плоским текстом для этого места (лучше не тронуть, чем собрать
  неправильную дробь).
- Один уровень вложенности (дробь внутри числителя/знаменателя другой дроби)
  обрабатывается на best-effort основе; корректность для более глубокой
  вложенности не гарантируется (см. Out of scope).

## User stories / flow

1. Пользователь загружает демо-ОГЭ с заданием 6: `Найдите значение выражения
   1/(1/30+1/42)` — эта страница текстовая, минует vision. После изменения:
   `page_text_from_dict` распознаёт черту дроби, строит `\frac{1}{\frac{1}{30}+\frac{1}{42}}`
   (или, при неуверенности в вложенном случае, хотя бы внешнюю
   `\frac{1}{...}`), контекст для генерации содержит эту дробь как LaTeX.
2. Генерирующая модель составляет свой вопрос с новой дробью (не скопированной
   дословно из источника) — благодаря новой инструкции в `SYSTEM_PROMPT`, пишет
   её как `$\frac{a}{b}$`, а не `a/b`.
3. Фронтенд рендерит обе дроби как настоящие дроби через уже существующий KaTeX
   в `RichText.tsx` — без изменений на фронте.

## Out of scope

- Восстановление матриц, интегралов с пределами, систем уравнений, многоэтажных
  выражений сложнее одного уровня вложенных дробей.
- Гарантированное распознавание 100% дробей на произвольных PDF — эвристика
  best-effort с безопасной деградацией к текущему плоскому тексту при
  неоднозначности.
- Изменения в vision-пути (`VISION_SYSTEM_PROMPT`) — там LaTeX уже запрашивается
  корректно, менять нечего.
- OCR или иной подход к распознаванию, не основанный на существующей связке
  pymupdf `get_text("dict")` + `get_drawings()`.
- Изменения во фронтенде — `RichText.tsx` уже поддерживает нужные разделители.

## Acceptance criteria

- [ ] `SYSTEM_PROMPT` явно требует LaTeX (`$...$`/`$$...$$`, `\frac{}{}`) для
      математики в сгенерированных вопросах/вариантах/объяснениях.
- [ ] Повторное извлечение задания 6/8-типа фракций из
      `ma_9_oge_2026_demo-5_cropped.pdf` (страница без картинок, но с
      Symbol-шрифтом) на "холодном" (не из кэша) прогоне даёт в извлечённом
      markdown `\frac{a}{b}`, обёрнутое в `$...$`, вместо плоской строки `a/b`.
- [ ] Когда эвристика не может однозначно сгруппировать числитель/знаменатель —
      извлечённый текст не отличается от сегодняшнего (нет регрессии, нет
      "сломанной" частичной дроби).
- [ ] Сгенерированный тест визуально показывает дроби с горизонтальной чертой
      (через существующий KaTeX-рендер), а не строкой `a/(b+c)`.
