# Явный выбор типов данных в документе вместо LLM-классификации

## Problem

Перед генерацией теста бэкенд делает отдельный LLM-вызов (`analyze_sources`),
чтобы угадать, что за документ загружен (теория / спецификация / образец). Это
лишний платный вызов и лишняя задержка на каждый запрос, а результат — эвристика,
которая может ошибиться (и мягко деградирует в "теория"). Пользователь при этом
и так знает, что он загружает. CEO решил: пусть пользователь сам указывает, какие
типы данных содержит документ, а этап анализа убирается полностью.

## Current behavior

- `backend/app/main.py`: поле формы `source_mode` (`auto` | `material` |
  `specification`). При `material` анализ подставляется без LLM; иначе вызывается
  `analyze_sources(context)`; при `specification` к найденным `kinds` принудительно
  добавляется `specification`.
- `backend/app/llm.py::analyze_sources` (промпт `ANALYZE_SYSTEM_PROMPT`, схема
  `ANALYSIS_JSON_SCHEMA`) возвращает `SourceAnalysis`: `kinds` (мультивыбор из
  `SourceKind`), `summary`, `exam_structure`, `topics`, `task_types`,
  `sample_tasks`. При сбое — тихий откат на `kinds=[material]`.
- `backend/app/llm.py::build_user_prompt`: ветки определяются результатом анализа —
  `spec_like` (есть `specification` или `sample`) и `has_material` (есть
  `material`). В ветке `spec_like` в промпт добавляется врезка `_format_analysis`
  (summary, структура экзамена, темы, типы заданий, примеры заданий), затем полный
  текст документа.
- `backend/app/schemas.py`: `SourceKind`, `SourceAnalysis`; `GenerateResponse.analysis`.
- `frontend/src/components/UploadForm.tsx`: выпадающий список "Что за документ"
  (`sourceMode`, один вариант из трёх). `frontend/src/api.ts` отправляет
  `source_mode`. `frontend/src/App.tsx` показывает плашку "Документ распознан как
  спецификацию/образец" по `result.analysis`.
- Зависимые тесты: `backend/tests/test_generate.py` (мок `generate_quiz` с
  параметром `analysis`, форма с `source_mode`), `frontend/src/api.test.ts`
  (`sourceMode: "auto"`).

## Solution

1. **Пользователь выбирает типы.** В форме — мультивыбор (чекбоксы/чипы, как у
   "Типы вопросов") из `material` (теория/конспект), `specification`
   (спецификация экзамена / список тем), `sample` (образец варианта / примеры
   заданий). Можно выбрать несколько одновременно. По умолчанию выбран `material`
   (совпадает с наиболее частым сценарием и прежним дефолтным поведением "теория").
   Выбор относится ко всем загруженным файлам сразу (один набор типов на запрос,
   как и раньше один `source_mode` на запрос) — не per-file.
2. **Этап анализа удаляется полностью.** Из `llm.py` удаляются `analyze_sources`,
   `ANALYZE_SYSTEM_PROMPT`, `ANALYSIS_JSON_SCHEMA`, `_format_analysis`; из
   `schemas.py` — `SourceAnalysis`; из `GenerateResponse` — поле `analysis`. Один
   LLM-вызов на запрос вместо двух (не считая vision).
3. **Промпт строится только по выбранным типам и полному тексту.** Структурная
   врезка (summary/topics/task_types/sample_tasks) не нужна: она была результатом
   анализа, а без анализа её нечем заполнить, и отдельный вызов ради неё
   возвращал бы удалённый этап. Модель и так получает полный текст документа
   ("Полный текст документа для справки" в ветке `spec_like`) — этого достаточно.
   Осознанный компромисс: без предварительной выжимки тем/типов модель сама
   извлекает их из текста в том же вызове.
   Ветки `build_user_prompt` по выбранным типам:
   - `spec_like = specification ∈ kinds или sample ∈ kinds`; `has_material =
     material ∈ kinds` — те же условия, что сегодня, но по выбору пользователя.
   - Если `spec_like`: сохраняется текущее предупреждение "это не учебная теория,
     а описание экзамена; не задавай вопросов про сам документ; составь НОВЫЙ тест
     из N заданий, воспроизводящий темы/типы/сложность". Формулировка уточняется
     по выбранным типам: если выбран `specification` — "воспроизводи перечисленные
     темы и структуру"; если выбран `sample` — "по образцу приведённых заданий,
     придумывай свои условия и числа". Если выбраны оба — обе фразы.
   - Если при `spec_like` выбран ещё и `material` — сохраняется текущая фраза
     "опирайся на теорию как на источник фактов, но вопросы строй в формате
     заданий экзамена".
   - Иначе (только `material`) — текущая ветка "Материал: ... Составь ровно N
     вопросов".
   - Для `spec_like` полный текст по-прежнему передаётся как справка.
4. **Валидация.** Хотя бы один тип обязателен. Значения вне
   `material|specification|sample` отбрасываются (как для `question_types`); если
   после фильтрации список пуст — `422`. Если поле не передано вообще — дефолт
   `material` (запрос старого вида без нового поля не ломается).
5. **Поле `source_mode` удаляется.** Отдельного значения `auto` больше нет —
   автоопределения не существует.
6. **Плашка "Документ распознан как ..." на фронте удаляется** (`App.tsx`): она
   отображала результат анализа, которого больше нет; пользователь сам выбрал
   типы, подтверждать их обратно не нужно.

## User stories / flow

1. Пользователь загружает демоверсию ОГЭ и отмечает "Образец варианта" — тест
   генерируется в формате заданий образца, один LLM-вызов.
2. Пользователь загружает спецификацию + образец в одном PDF и отмечает оба типа
   — промпт получает обе формулировки.
3. Пользователь загружает конспект и оставляет дефолт "Теория" — поведение как
   сегодня в режиме `material`.
4. Пользователь снимает все галочки — кнопка "Создать тест" неактивна (на бэкенде
   при обходе UI — `422`).

## Out of scope

- Выбор типов отдельно для каждого файла.
- Возврат к автоопределению как опции (`auto`) — CEO решил убрать полностью.
- Замена врезки анализа на другой механизм предвыделения тем/заданий.
- Определение количества вопросов по образцу — вынесено в `auto-question-count`
  (зависит от этой спеки, см. там).
- Показ пользователю плашки/сводки "как понят документ".

## Acceptance criteria

- [ ] В пайплайне `/api/generate` нет вызова `analyze_sources`: `analyze_sources`,
      `SourceAnalysis`, `_format_analysis` и `GenerateResponse.analysis`
      удалены; на запрос приходится один LLM-вызов генерации (плюс vision).
- [ ] Новое поле формы `source_kinds` (список через запятую) определяет ветки
      `build_user_prompt`; `source_mode` удалён.
- [ ] Выбор нескольких типов одновременно (например, `specification,sample`)
      корректно отражается в промпте; `material`-only даёт текущий промпт теории.
- [ ] Пустой/некорректный `source_kinds` → `422`; отсутствие поля → `material`.
- [ ] Форма содержит мультивыбор типов, по умолчанию `material`; при пустом выборе
      отправка заблокирована.
- [ ] Плашка на основе `result.analysis` в `App.tsx` удалена; `types.ts` не
      содержит `SourceAnalysis`/`analysis`.
- [ ] Существующие тесты (`backend/tests/test_generate.py`, `frontend/src/api.test.ts`)
      обновлены под новый контракт.
