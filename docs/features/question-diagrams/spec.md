# Диаграммы (числовая прямая и др.) в сгенерированных вопросах

## Problem

Источники (например, демоверсии ОГЭ) содержат задания, условие которых опирается
на графическую иллюстрацию — типичный пример: точка, отмеченная на числовой
прямой, где сам рисунок необходим, чтобы ответить на вопрос. Сегодня такие
иллюстрации теряются на этапе распознавания: попадая в текстовый контекст как
словесное описание, они либо не используются моделью при составлении вопроса,
либо превращаются в неполное текстовое описание — и итоговый вопрос либо
пропускает эту часть условия, либо становится нерешаемым без картинки, которой
нет. У системы в принципе нет способа доставить реальное изображение до
пользователя: ни в схеме вопроса, ни во фронтенде нет для этого места.

## Current behavior

- `backend/app/text_extract.py::_page_needs_vision()` отправляет "тяжёлые"
  страницы (мало текста и/или есть изображения) в vision-модель.
- `VISION_SYSTEM_PROMPT` (`backend/app/llm.py`) инструктирует модель переносить
  любой график/чертёж/иллюстрацию в **словесное** описание в квадратных скобках:
  `[Рисунок: ...]`. Само изображение никак не сохраняется.
- `backend/app/schemas.py::Question` не имеет поля для изображения — модель
  вопроса полностью текстовая (`text`, `options`, `correct_text`, `explanation`).
- `build_user_prompt`/`SYSTEM_PROMPT` (генерация теста) не содержат инструкции
  использовать блоки `[Рисунок: ...]` из контекста при составлении вопросов —
  ничто не мешает модели просто отбросить эту часть материала.
- Фронтенд (`frontend/src/components/QuizView.tsx`, `RichText.tsx`) не имеет
  компонента для рендера изображения — есть только рендер текста и формул через
  KaTeX.

## Solution

### 1. Vision-распознавание страницы возвращает изображения, а не только текст

`transcribe_page` (`backend/app/llm.py`) вместо обычного текстового ответа
запрашивает у vision-модели структурированный JSON (по аналогии с
`analyze_sources`/`SourceAnalysis`, через `response_format=json_schema`):

```python
class PageDiagram(BaseModel):
    id: str            # уникальный в рамках страницы идентификатор, например "d1"
    alt_text: str       # словесное описание рисунка (как сегодня в "[Рисунок: ...]")
    bbox: list[float]   # [x0, y0, x1, y1], доли от размеров страницы (0..1)

class PageTranscription(BaseModel):
    markdown: str        # текст страницы, как сегодня
    diagrams: list[PageDiagram] = []
```

`VISION_SYSTEM_PROMPT` дополняется инструкцией: для каждого графика/чертежа/
иллюстрации (включая числовую прямую) — добавить объект в `diagrams` с кратким
`alt_text` и приблизительным `bbox`, и вставить в `markdown` на месте рисунка
плейсхолдер `[Рисунок: <alt_text> | diagram_id=<id>]` (без изменений в остальной
части промпта).

### 2. Бэкенд вырезает изображение из уже отрендеренной страницы

В `_from_pdf` (`backend/app/text_extract.py`) страница уже рендерится в PNG для
отправки в vision-модель (`doc[idx].get_pixmap(dpi=settings.vision_dpi)`). Для
каждого `PageDiagram` из ответа бэкенд переводит `bbox` (доли 0..1) в пиксельные
координаты этого же пиксмапа и вырезает прямоугольник как отдельный PNG.

- Если `bbox` вырожден (нулевая площадь после клампа к границам страницы) —
  рисунок пропускается (в лог — warning), в тексте остаётся только словесное
  описание без картинки.
- Ограничение `vision_max_diagrams_per_page: int = 5` (новая настройка в
  `config.py`) — если модель вернула больше, лишние отбрасываются.

### 3. Результат извлечения кэшируется вместе с изображениями

Сегодня извлечение кэшируется на диске по SHA-256 файла как один `.md`-файл
(`_cache_file` в `text_extract.py`). Кэш расширяется: рядом с
`{sha256}.md` создаётся папка `{sha256}.diagrams/{diagram_id}.png` для каждого
вырезанного изображения. При попадании в кэш (повторная загрузка того же файла)
изображения читаются с диска — повторного вызова vision-модели не требуется.

`extract_text` возвращает не только текст, а текст + словарь
`{diagram_id: png_bytes}` (сигнатура функции меняется, вызывающий код в
`main.py` пробрасывает словарь дальше).

### 4. Вопрос может сослаться на изображение

`Question` (`backend/app/schemas.py`) получает новое поле:

```python
diagram_id: str | None = None  # id рисунка из контекста, на который ссылается вопрос
```

`SYSTEM_PROMPT`/`build_user_prompt` (генерация теста) получают инструкцию: если
для ответа на вопрос необходим рисунок, упомянутый в контексте как
`[Рисунок: ... | diagram_id=...]`, указать этот `diagram_id` в поле вопроса;
если рисунок не нужен — оставить `null`.

После получения и валидации `Quiz` от LLM (`generate_quiz`), бэкенд в
`main.py` разрешает `diagram_id` в реальные байты изображения: для каждого
вопроса с непустым `diagram_id`, если такой id есть среди изображений,
извлечённых из загруженных файлов — заполняет `question.diagram`
(см. `api-contract.md`) данными изображения в виде data URL; если `diagram_id`
не найден среди извлечённых изображений (модель сослалась на несуществующий id
или диаграмма не сохранилась) — `diagram` остаётся `null`, вопрос не падает и не
ретраится. Публичный ответ API не должен содержать сырой `diagram_id` — только
разрешённое поле `diagram`.

### 5. Фронтенд рендерит изображение

Новый компонент `frontend/src/components/QuestionDiagram.tsx`: рендерит
`<img>` с `src` = `diagram.image_base64` и `alt` = `diagram.alt_text`,
адаптивной ширины. `QuizView.tsx` рендерит `<QuestionDiagram diagram={q.diagram} />`
сразу после текста вопроса и до вариантов ответа, только если `q.diagram` не
`null`.

## User stories / flow

1. Пользователь загружает демоверсию ОГЭ с заданием "на числовой прямой отмечена
   точка A — какое это число?" (иллюстрация — числовая прямая с делениями).
2. Vision-распознавание страницы возвращает markdown с плейсхолдером
   `[Рисунок: числовая прямая от 0 до 1 с шагом 0,1, точка A между 0,5 и 0,6 |
   diagram_id=d1]` и список `diagrams` с `bbox` этого рисунка.
3. Бэкенд вырезает изображение числовой прямой и кладёт его в кэш.
4. Генерация теста: модель составляет вопрос по этому заданию и указывает
   `diagram_id: "d1"`.
5. Бэкенд разрешает `d1` в реальные байты картинки, кладёт в `question.diagram`.
6. Фронтенд показывает вопрос с настоящим изображением числовой прямой над
   вариантами ответов.

## Out of scope

- Векторный/SVG-рендер диаграмм — только растровый PNG-кроп уже отрендеренной
  страницы.
- Диаграммы для docx/txt/md — у этих форматов нет постраничного рендера и
  vision-конвейера; для них `diagram` всегда `null` (без изменений).
- Восстановление диаграмм для страниц, которые не попали в vision (`vision_enabled`
  выключен, лимит `vision_max_pages` исчерпан) — поведение как сегодня (нет рисунка).
- Редактирование/загрузка собственных изображений пользователем.
- Гарантия, что LLM всегда правильно свяжет вопрос с нужным `diagram_id` —
  best-effort через промпт, без валидации смыслового соответствия.
- Постоянное публичное хранилище изображений (CDN, отдельный `/api/assets`
  эндпоинт) — изображения передаются инлайн как data URL в ответе `/api/generate`,
  кэш на диске служит только для избежания повторных vision-вызовов.

## Acceptance criteria

- [ ] Генерация теста из демо-PDF с числовой прямой (`ma_9_oge_2026_demo-5_cropped.pdf`,
      задание 7) даёт вопрос с непустым `diagram`, изображение которого визуально
      показывает числовую прямую с отмеченной точкой.
- [ ] Вопросы без релевантного рисунка в исходнике имеют `diagram: null`, поведение
      не отличается от текущего.
- [ ] Повторная генерация из того же файла (тот же SHA-256) не вызывает
      vision-модель повторно — изображения берутся из кэша на диске.
- [ ] Если LLM вернула `diagram_id`, не найденный среди извлечённых из документов
      изображений — запрос не падает, `question.diagram` — `null`.
- [ ] `diagram_id` не присутствует в публичном JSON-ответе `/api/generate` — только
      `diagram`.
- [ ] Фронтенд рендерит `QuestionDiagram` только когда `q.diagram` не `null`.
