# Генерация рисунков к вопросам через TikZ → SVG

## Problem

Тест — это **новые** задания, аналогичные заданиям из источника: LLM меняет
числа и условия. Если исходное задание опиралось на рисунок (числовая прямая,
треугольник, график функции, электрическая схема, окружность и т.п.), новому
заданию нужен **новый** рисунок под новые числа. Картинку из PDF переиспользовать
нельзя: она иллюстрирует старые числа.

Сегодня так и происходит на демоверсии ОГЭ (`ma_9_oge_2026_demo-5_cropped.pdf`):
в задании «точка A на числовой прямой» LLM придумала новые дроби (6/11, 7/11…),
поняла, что вырезанный из PDF рисунок им не соответствует, и выставила
`diagram_id: null`, описав положение точки словами. Пользователь получил
задание без рисунка.

Нужен способ рисовать **произвольные** школьные/учебные рисунки (геометрия,
графики функций, числовые и координатные прямые, схемы из физики) — дёшево,
корректно и без отдельного рендерера под каждый тип рисунка на клиенте.

## Current behavior

Сейчас действует механизм из фичи `question-diagrams` (эта фича его **заменяет
полностью**):

- `backend/app/llm.py::VISION_SYSTEM_PROMPT` просит vision-модель для каждого
  рисунка вернуть `PageDiagram{id, alt_text, bbox}` и вставить в markdown
  плейсхолдер `[Рисунок: <alt_text> | diagram_id=<id>]`.
- `backend/app/text_extract.py::_from_pdf` вырезает по `bbox` PNG из
  отрендеренной страницы (`_crop_diagram`), переименовывает id в
  `<sha8>_p<N>_<id>` и возвращает словарь `{diagram_id: png}`;
  `extract_text` кэширует PNG в `<ingest_cache_dir>/<sha256>.diagrams/`.
  Ограничение — `settings.vision_max_diagrams_per_page`.
- `backend/app/schemas.py::Question.diagram_id` (скрыт из API,
  `exclude=True`) заполняется LLM при генерации; `SYSTEM_PROMPT` просит указать
  `diagram_id` из плейсхолдера, если рисунок нужен.
- `backend/app/main.py` (после `generate_quiz`) по `diagram_id` подставляет
  PNG в `Question.diagram = Diagram(image_base64="data:image/png;base64,…",
  alt_text=…)`; `_PLACEHOLDER_RE` достаёт `alt_text` из контекста.
- Фронтенд: `frontend/src/components/QuestionDiagram.tsx` рендерит
  `<figure className="paper fig"><img/><figcaption>{alt_text}</figcaption></figure>`.

Проблема не в коде, а в самой идее: рисунок из источника по определению не
соответствует новому заданию.

## Solution

Общий поток:

```
файл → извлечение текста (vision только для «тяжёлых» страниц;
       рисунок → подробное текстовое описание, без вырезания картинки)
     → LLM генерирует тест: у вопроса, которому нужен рисунок, — поле tikz
       (исходник нового рисунка под новые числа)
     → бэкенд компилирует каждый tikz в SVG (tectonic → PDF → PyMuPDF → SVG)
       ошибка компиляции → LLM исправляет (до 2 раз) → иначе вопрос удаляется
     → Question.diagram = SVG data URL → SSE result → фронт показывает <img>
```

### 1. Удаляем механизм вырезания и переиспользования картинок из PDF

- `PageDiagram`, поле `diagrams` в `PageTranscription`, `bbox` — удаляются.
  `PageTranscription` содержит только `markdown`.
- `text_extract.py`: удаляются `_crop_diagram`, `_diagrams_dir`, переименование
  id, запись/чтение `*.diagrams/`. `extract_text` снова возвращает только текст
  (`str`), вызывающий код в `main.py` упрощается соответственно.
- `config.py`: удаляется `vision_max_diagrams_per_page`.
- `schemas.py`: удаляется `Question.diagram_id`.
- `main.py`: удаляются `_PLACEHOLDER_RE` и подстановка PNG по `diagram_id`.
- **Версия ingest-кэша.** Старые закэшированные `.md` содержат плейсхолдеры с
  `diagram_id` и краткие описания. Имя кэш-файла получает версию (например,
  `<sha256>.v2.md`), чтобы старые записи не использовались. Старые файлы и
  папки `*.diagrams` не удаляем программно — просто игнорируются.

### 2. Vision описывает рисунок подробно

`VISION_SYSTEM_PROMPT`: каждый рисунок (график, чертёж, схема, числовая/
координатная прямая, таблица-рисунок) переносится в markdown как
`[Рисунок: <подробное описание>]`. Описание должно быть достаточным, чтобы по
нему нарисовать аналогичный рисунок: тип рисунка; все числа, подписи, деления,
отмеченные точки и их примерное положение; для геометрии — фигуры, вершины,
отмеченные углы/длины; для графиков — оси, диапазоны, вид кривой; для схем —
элементы и как они соединены. Без id.

### 3. LLM генерирует исходник рисунка в поле `tikz`

- `Question` получает внутреннее поле `tikz: str | None = Field(default=None,
  exclude=True)` — видно LLM в JSON-схеме (`QUIZ_JSON_SCHEMA`), в ответ API
  не попадает.
- `SYSTEM_PROMPT` / `build_user_prompt` — правила:
  - если исходное задание в материале содержит `[Рисунок: …]` и для ответа
    рисунок нужен, аналогичный вопрос **обязан** иметь `tikz` — рисунок под
    **новые** числа вопроса; иначе `tikz = null`;
  - `tikz` — ровно одно окружение `\begin{tikzpicture}…\end{tikzpicture}` или
    `\begin{circuitikz}…\end{circuitikz}`, без преамбулы, `\documentclass`,
    `\usepackage`;
  - доступные пакеты и библиотеки перечисляются в промпте (ровно те, что в
    шаблоне, см. п. 4);
  - координаты и положения вычисляются из чисел условия (точка A=6/11 стоит в
    6/11, а не «где-то между 0,5 и 0,6»);
  - рисунок не должен подсказывать ответ (не подписывать искомую величину);
  - подписи — в `$…$`, русский текст допустим;
  - ширина рисунка — не больше ~10 см; графики функций — через `pgfplots`
    `axis`, подписи внутри осей — в пределах `xmin..xmax`/`ymin..ymax`;
    электрические схемы — через `circuitikz`.

### 4. Новый модуль `backend/app/diagrams.py` — компиляция TikZ → SVG

Вся компиляция идёт на бэкенде, в процессе FastAPI, через внешний бинарник
`tectonic` (в subprocess). Фронтенд получает готовый SVG.

Публичный интерфейс:

```python
class TikzError(Exception):
    log: str          # выжимка ошибки для LLM (см. ниже)

async def render_tikz(body: str) -> bytes   # SVG-байты или TikzError
async def warmup() -> None                  # см. п. 6
```

Шаги `render_tikz`:

1. **Проверка до компиляции** (чистый Python):
   - ровно одно окружение `tikzpicture` или `circuitikz` верхнего уровня
     (вложенные `axis` и т.п. внутри — нормально);
   - длина ≤ `settings.tikz_max_chars` (по умолчанию 8000);
   - нет запрещённых команд: `\input`, `\include`, `\openin`, `\openout`,
     `\write`, `\read`, `\catcode`, `\usepackage`, `\documentclass`,
     `\immediate`, `\newread`, `\newwrite`;
   - нарушение → `TikzError` с человекочитаемой причиной (идёт в цикл
     исправления, как ошибка компиляции).
2. **Сборка `.tex`** по фиксированному шаблону, в который вставляется тело.
   Шаблон проверен на практике (tectonic 0.17, macOS):

   ```latex
   \documentclass[border=4pt]{standalone}
   \usepackage{fontspec}
   \setmainfont{cmunrm}[Extension=.otf, BoldFont=cmunbx, ItalicFont=cmunti, BoldItalicFont=cmunbi]
   \usepackage{tikz}
   \usepackage{pgfplots}
   \usepackage[european]{circuitikz}
   \usetikzlibrary{calc,angles,quotes,intersections,arrows.meta,patterns,decorations.markings}
   \pgfplotsset{compat=1.18}
   \begin{document}
   <тело>
   \end{document}
   ```

   - `standalone` сам обрезает холст по рисунку.
   - Шрифт CMU Serif (Computer Modern с кириллицей) подключается **по имени
     файла** — по названию семейства tectonic его не находит (проверено).
   - `[european]` — обозначения элементов цепей в европейском стиле, как в
     российских учебниках (резистор — прямоугольник).
3. **Компиляция**: во временной директории
   `tectonic -X compile fig.tex --untrusted --only-cached --outfmt pdf`
   через `asyncio.create_subprocess_exec`, таймаут
   `settings.tikz_timeout_s` (по умолчанию 20 с), по таймауту процесс
   убивается → `TikzError("превышено время компиляции")`.
   - `--untrusted` — запрет shell-escape и прочих небезопасных возможностей.
   - `--only-cached` — никаких сетевых скачиваний в рантайме.
   - код возврата ≠ 0 → `TikzError(log)`, где `log` — строки ошибок из вывода
     (`error: fig.tex:<N>: …`, строки на `!`, до ~15 строк), **номера строк
     пересчитаны в строки тела** (минус число строк преамбулы), чтобы LLM
     понимала, где ошибка в её коде.
4. **PDF → SVG** через PyMuPDF (уже в зависимостях):
   `pymupdf.open(pdf)[0].get_svg_image(text_as_path=True)` — текст
   превращается в кривые, SVG не зависит от шрифтов браузера. Проверено:
   растр SVG совпадает с растром PDF.
5. Временная директория удаляется в любом случае.

Замеры прототипа (M-серия Mac, прогретый кэш): компиляция одного рисунка
~1–1,5 с, 5 рисунков параллельно ~1,5 с, конвертация в SVG — миллисекунды,
размер SVG 7–16 КБ.

### 5. Оркестрация: этап «рисуем схемы» + цикл исправления

В `main.py` после успешного `generate_quiz` (и обрезки до `max_questions`):

- Если ни у одного вопроса нет `tikz` — этап пропускается целиком (событие
  не шлётся).
- Иначе шлётся SSE-прогресс `stage="diagrams"` с `{processed: 0, total: N}`
  (N — число вопросов с `tikz`), затем все рисунки обрабатываются
  параллельно (`asyncio.gather` + `asyncio.Semaphore(settings.tikz_concurrency)`,
  по умолчанию 4). После завершения каждого рисунка (успех или удаление
  вопроса) — событие с увеличенным `processed`.
- Для каждого вопроса:
  1. `render_tikz(q.tikz)` → успех → `q.diagram = Diagram(
     image_base64="data:image/svg+xml;base64,<…>", alt_text="")`.
  2. `TikzError` → `llm.fix_tikz(question_text, tikz, error_log)` — отдельный
     небольшой LLM-запрос (условие вопроса + исходник + ошибка), ответ по
     JSON-схеме `{"tikz": "…"}` → снова `render_tikz`.
  3. Исправлений — не больше `settings.tikz_fix_attempts` (по умолчанию 2),
     т.е. максимум 3 компиляции на рисунок. Ошибка самого LLM-вызова
     исправления (сеть, невалидный JSON) считается неудачной попыткой.
  4. Все попытки неудачны → вопрос **удаляется из теста**, `log.warning`
     с id вопроса и последней ошибкой.
- После этапа оставшиеся вопросы перенумеровываются `id = 1..n` по порядку.
- Если удалены **все** вопросы — SSE-событие `error` с текстом
  «Не удалось построить рисунки ни для одного вопроса» (формат ошибки — как
  у других ошибок потока).
- Каждый рендер и каждый вызов `fix_tikz` оборачивается в `stage()` из
  `obs.py` (время, номер попытки, успех/ошибка).

### 6. Прогрев и зависимости окружения

- Системная зависимость: `tectonic` (macOS — `brew install tectonic`, Linux —
  официальный бинарник). Путь к бинарнику — `settings.tikz_bin`
  (по умолчанию `"tectonic"`). Новых Python-зависимостей нет.
- При первом запуске tectonic скачивает пакеты в свой кэш
  (`~/.cache/Tectonic` / `~/Library/Caches/Tectonic`); в прототипе это заняло
  1,5–2,5 минуты, дальше офлайн.
- `diagrams.warmup()` вызывается в lifespan FastAPI при старте:
  - бинарник не найден → старт падает с понятной ошибкой
    («tectonic не найден: установите …»);
  - компилирует эталонный рисунок, использующий все пакеты шаблона,
    **без** `--only-cached` (чтобы при необходимости докачать пакеты);
    ошибка прогрева → `log.error`, сервер стартует (рисунки в запросах будут
    падать → вопросы удаляться — это видно в логах).
- `README.md`: раздел про установку tectonic и то, что первый старт бэкенда
  может занять несколько минут.

### 7. Фронтенд

- `QuestionDiagram.tsx`: `<figcaption>` рендерится только при непустом
  `alt_text` (у сгенерированных рисунков он всегда пустой); `alt` у `<img>` —
  `"Рисунок к заданию"`, если `alt_text` пуст. Подложка `.paper fig`
  остаётся: у SVG прозрачный фон, на стеклянном UI без белой подложки он
  нечитаем.
- `GenerationProgress.tsx`: новый шаг «Рисуем схемы» (`stage="diagrams"`,
  detail `«k из N»`). Шаг показывается в списке только если событие
  `diagrams` пришло (у тестов без рисунков его нет).
- `types.ts` / `api.ts` — новый stage и тип detail (см. `api-contract.md`).

## User stories / flow

1. Пользователь загружает `ma_9_oge_2026_demo-5_cropped.pdf` (задания 5–9,
   в задании 7 — числовая прямая с точкой A).
2. Vision распознаёт страницу; числовая прямая попадает в контекст как
   `[Рисунок: числовая прямая с делениями через 0,1 от 0 до 1, подписаны 0,
   0,5 и 1; точка A отмечена между 0,5 и 0,6, ближе к 0,6]`.
3. LLM генерирует аналог задания 7 с дробями 6/11, 7/11, 8/11, 9/11 и поле
   `tikz` — числовая прямая, на которой точка A стоит в 6/11.
4. Прогресс показывает «Извлекаем текст» → «Составляем тест» → «Рисуем схемы
   1 из 1».
5. Бэкенд компилирует TikZ в SVG; пользователь видит задание с рисунком
   числовой прямой на белой подложке, без подписи под рисунком.
6. Если TikZ не скомпилировался — LLM исправляет; если за 2 исправления не
   вышло — задание в тест не попадает (в тесте на 1 вопрос меньше).

## Out of scope

- Переиспользование картинок из исходного документа — удаляется намеренно.
- Проверка смысловой корректности рисунка (что точка стоит там, где надо) —
  только правилами в промпте; vision-проверки сгенерированного рисунка нет.
- Генерация растровых изображений image-моделями.
- Сообщение пользователю в UI о том, что часть вопросов удалена (только лог).
- Кэширование скомпилированных рисунков.
- Рисунки в `options` и `explanation` — только один рисунок на вопрос, под
  условием.
- Docker/деплой-конфигурация — только README и настройка пути к бинарнику.
- Санитизация SVG: SVG показывается только через `<img>` (скрипты внутри
  не исполняются) и генерируется нашим же пайплайном из PDF.

## Acceptance criteria

- [ ] В кодовой базе не осталось `diagram_id`, `PageDiagram`, `bbox`,
      `_crop_diagram`, `_diagrams_dir`, `_PLACEHOLDER_RE`,
      `vision_max_diagrams_per_page`; `extract_text` возвращает `str`.
- [ ] Ingest-кэш версионирован: файл, закэшированный до фичи, не
      используется повторно.
- [ ] `VISION_SYSTEM_PROMPT` требует подробное описание рисунка в формате
      `[Рисунок: …]` без id.
- [ ] `Question.tikz` есть в JSON-схеме для LLM и отсутствует в ответе API.
- [ ] `render_tikz` на корректном теле (числовая прямая, треугольник с
      `angles`/`quotes`, парабола `pgfplots`, цепь `circuitikz` с кириллической
      подписью) возвращает валидный SVG, начинающийся с `<svg` (тест
      пропускается через `pytest.mark.skipif`, если `tectonic` не установлен).
- [ ] `render_tikz` бросает `TikzError`: на опечатке в команде (лог содержит
      номер строки **тела**, а не собранного файла); на `\input{/etc/passwd}`,
      `\write18`, `\usepackage{…}` — без запуска компилятора; на двух
      окружениях `tikzpicture`; на превышении `tikz_max_chars`; на таймауте.
- [ ] Оркестрация (тесты с замоканными `render_tikz`/`fix_tikz`): успех с
      первой попытки → `diagram` с `data:image/svg+xml;base64,` и
      `alt_text == ""`; успех после 1 исправления; после 3 неудачных компиляций
      вопрос удаляется, остальные перенумерованы `1..n`; удалены все →
      SSE-событие `error`; вопросы без `tikz` не трогаются.
- [ ] SSE: при наличии рисунков приходят события `stage="diagrams"` с
      `processed` от 0 до N; без рисунков событий `diagrams` нет.
- [ ] `warmup()`: отсутствующий бинарник → старт приложения падает с
      понятным сообщением.
- [ ] Фронт: шаг «Рисуем схемы» появляется только при событии `diagrams`;
      `figcaption` не рендерится при пустом `alt_text`.
- [ ] Фронт: рисунок отображается на бумажной подложке — `<img>` внутри
      `figure` с классами `paper fig` (белый фон, рамка, тень из `.paper`
      в `index.css`); формулы при этом подложки не имеют (`RichText` не
      использует класс `paper`).
- [ ] README описывает установку tectonic и долгий первый старт.
- [ ] `uv run ruff check .`, `uv run pytest -q`, `npm run lint`,
      `npm run test`, `npm run build` — чистые.
