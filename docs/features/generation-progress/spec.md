# Прогресс генерации теста в реальном времени

## Problem

`POST /api/generate` сегодня — обычный синхронный запрос: пользователь жмёт
«Создать тест», видит спиннер с текстом «Генерируем…» и ждёт от нескольких
секунд до пары минут (vision-распознавание "тяжёлых" страниц PDF по одной +
генерация теста LLM), не понимая, что происходит и сколько ещё ждать. Это
особенно заметно на больших PDF, где vision-модель обрабатывает страницы
последовательно/ограниченно параллельно и может занимать заметную часть
времени ответа.

Нужно показывать пользователю реальный прогресс обработки — какие шаги уже
пройдены и что происходит сейчас — а не выдуманные заранее стадии. Показываемые
шаги должны отражать фактическую работу бэкенда, а не пустую анимацию.

## Current behavior

- `backend/app/main.py::generate()` — один `async def`, который последовательно
  делает: чтение файлов → `extract_text()` на каждый (может включать
  vision-распознавание PDF-страниц внутри `_from_pdf()`,
  `backend/app/text_extract.py`) → `combine()` → `generate_quiz()`
  (`backend/app/llm.py`, один LLM-вызов с ретраем на невалидный JSON) →
  разрешение `diagram_id` → единый JSON-ответ.
- Единственная сегодняшняя обсервабилити — серверные логи через
  `obs.py::stage()` (`→ name` / `✓ name done in Xs`); наружу, к фронтенду,
  ничего из этого не идёт.
- `frontend/src/api.ts::generateQuiz()` — `fetch` с обычным `await resp.json()`;
  `App.tsx` держит булевый `loading` и показывает статичный текст
  «Генерируем…» (`UploadForm.tsx:170`) до получения полного ответа или ошибки.
- Внутри `_from_pdf()` "тяжёлые" страницы обрабатываются параллельно через
  `asyncio.gather()` — результат собирается только когда обработаны вообще все
  страницы, промежуточного сигнала о готовности отдельной страницы нет.

## Solution

### Реальные этапы, которые показываем

Ровно два укрупнённых шага, соответствующих фактической работе бэкенда:

1. **`extract`** — извлечение текста из всех загруженных файлов и сборка
   контекста (`extract_text()` по каждому файлу + `combine()`). Внутри этого
   шага, для PDF, `detail` несёт структурированный прогресс по страницам
   этого файла (см. "Формат `detail`" ниже) — не только по "тяжёлым",
   уходящим в vision, а по всем страницам документа.
2. **`generate`** — вызов LLM на генерацию теста (`generate_quiz()`),
   включая случай ретрая при невалидном JSON-ответе модели (реальный второй
   LLM-вызов, а не фиктивный отдельный шаг «проверяем ответы»).

Шаг `extract` не эмитится вообще, если сегодня для файла ничего не нужно
показать раньше, чем через доли секунды (например, `.txt`/`.md` или
PDF/DOCX без тяжёлых страниц) — сообщение о начале файла шлётся всё равно
(дёшево и упрощает реализацию), просто не задерживается ожиданием.

### Формат `detail` — структурированный, не привязан к языку

`detail` шага `extract` — не человекочитаемая фраза, а JSON-объект (или
`null`), чтобы фронтенд сам формировал текст на нужном языке, а не парсил
русские строки:

```ts
type ExtractDetail = {
  filename: string;
  processed: number;  // страниц файла уже обработано
  total: number;       // всего страниц в файле; 0 — если формат файла
                        // не постраничный (docx/txt/md) или прогресс не считается
} | null;
```

Для PDF `total` — общее число страниц документа (не только "тяжёлых",
уходящих в vision). `processed` растёт в двух фазах:
1. Сразу после локального прохода pymupdf4llm (без LLM, доли секунды) —
   единомоментно поднимается до `total − <число "тяжёлых" страниц>` (все
   страницы, не нуждающиеся в vision, уже готовы).
2. Дальше — по одной единице за каждую завершившуюся vision-страницу, пока
   не достигнет `total`.

Для docx/txt/md (нет понятия "страница" в текущем извлечении) —
`{filename, processed: 0, total: 0}`; фронтенд в этом случае показывает
только `filename`, без числового прогресса.

Шаг `generate` детали не структурирует — там `detail` остаётся строкой на
русском (`string | null`), т.к. там нет числового прогресса, только
качественная пометка "идёт ретрай" — см. `api-contract.md`.

Никаких дополнительных LLM-вызовов ради более гранулярных "фейковых" стадий
(«выделяем темы», «проверяем ответы» как отдельные шаги) не вводится — это
противоречило бы принципу "no speculative generality" и увеличило бы
стоимость и время каждого запроса к Polza.ai.

### Транспорт: Server-Sent Events в том же запросе

`POST /api/generate` остаётся одним запросом, но ответ становится потоковым
(`text/event-stream`) вместо разового JSON:

1. Валидация, которая не требует чтения байтов файлов (диапазон
   `num_questions`, пустой список файлов, `max_files`, отсутствие валидных
   `question_types`/`source_kinds`) выполняется **до** открытия потока — как
   и сегодня, эти случаи остаются обычными HTTP `422` с JSON-телом
   `{"detail": "..."}`.
2. После этого ответ HTTP всегда `200 text/event-stream` — заголовки статуса
   комитятся сразу, поэтому все ошибки, возникающие дальше по ходу обработки
   (файл превышает `max_file_size_mb`, неподдерживаемый формат, из файлов не
   извлёкся текст, сбой/невалидный ответ Polza.ai после ретрая) доставляются
   как SSE-событие `error`, а не HTTP-статусом. Это осознанное отличие от
   сегодняшнего поведения — см. `api-contract.md` для точного списка и для
   того, как `frontend/src/api.ts` должен различать эти два случая.
3. По ходу обработки бэкенд шлёт события `progress` с шагом (`extract` |
   `generate`) и человекочитаемой деталью (какой файл/страница, было ли
   ретрая). В конце — одно событие `result` с телом, эквивалентным сегодняшнему
   `GenerateResponse`, либо `error`.

### Бэкенд: emit-колбэк прокидывается по цепочке вызовов

Без выделенного джоб-стора и polling — прогресс явно эмитится через
колбэк-параметр, который прокидывается по вызовам внутри одного запроса:

- `main.py::generate()` создаёт `asyncio.Queue`, функцию
  `emit(stage: str, detail: str | None = None)` (`queue.put_nowait(...)`,
  синхронная — не требует `await` в местах вызова) и запускает всю текущую
  логику (`extract_text` по файлам → `combine` → `generate_quiz` → разрешение
  `diagram_id`) как фоновую `asyncio.Task`. Генератор потока читает из очереди
  и форматирует каждое сообщение как SSE-фрейм, пока задача не положит в
  очередь финальный `result`/`error` и сигнал конца.
- `extract_text()` и `_from_pdf()` (`text_extract.py`) принимают `emit` и
  вызывают его со структурированной деталью (см. "Формат `detail`" выше):
  один раз при начале обработки каждого файла (`processed=0`), один раз
  сразу после быстрого локального прохода по PDF (`processed` = число
  страниц, не ушедших в vision), и затем по одному разу за каждую
  завершившуюся vision-страницу (`processed` инкрементируется; порядок — по
  готовности, не по номеру страницы, т.к. распознавание идёт параллельно).
  Кэш-хит (файл уже распознавался раньше, см. `_cache_file`) не даёт
  постраничных событий — только событие начала файла.
- `generate_quiz()` (`llm.py`) принимает `emit` и вызывает его перед первым
  LLM-вызовом и перед каждым ретраем (с деталью о том, что предыдущий ответ не
  прошёл валидацию).
- `obs.py::stage()` не меняется и продолжает писать в серверные логи
  независимо от SSE — это разные механизмы для разных потребителей (логи для
  разработчика, SSE для пользователя).

### Фронтенд: чек-лист с текущим шагом

- `frontend/src/api.ts::generateQuiz()` меняет сигнатуру — принимает
  `onProgress: (stage: "extract" | "generate", detail: string | null) => void`,
  читает `resp.body` как поток, разбирает SSE-фреймы (`data: ...\n\n`) и
  резолвится тем же `GenerateResponse`, что и сегодня, либо бросает `Error` (из
  события `error`, как и раньше из HTTP-ошибки — вызывающий код в `App.tsx` не
  должен различать источник ошибки).
- `App.tsx` вместо булевого `loading` хранит текущий шаг и последнюю деталь
  (например `{stage: "extract" | "generate" | null, detail: string | null}`).
  Пока идёт генерация, вместо/над `UploadForm` показывается чек-лист из двух
  фиксированных строк (порядок всегда `extract` → `generate`, третьего шага
  нет):
  - «Извлекаем текст из документов»
  - «Составляем тест»

  Строка, соответствующая текущему `stage`, показывает спиннер и деталь
  (`detail`) вторым, более мелким текстом под заголовком строки (если
  `detail` есть); пройденные строки — галочку; ещё не начавшиеся — приглушены.
  Конкретную вёрстку и компонент решает `frontend-dev` в духе существующего
  стиля (`UploadForm.tsx`, `QuizView.tsx`), схема данных — см.
  `api-contract.md`.

## User stories / flow

1. Пользователь загружает PDF на 20 страниц, из которых 6 — "тяжёлые" (со
   сложной вёрсткой/картинками), и жмёт «Создать тест». Сразу видит строку
   «Извлекаем текст из документов» с деталью `{filename: "demo.pdf",
   processed: 0, total: 20}`, которая почти сразу сменяется на
   `processed: 14` (остальные 14 страниц обработаны локально без LLM), а
   затем по одной подрастает до `processed: 15, 16, ... 20` по мере готовности
   vision-страниц. Конкретный текст ("страница 15 из 20" и т.п.) формирует
   фронтенд из этих чисел.
2. Как только весь текст извлечён и собран контекст, строка «Извлекаем текст…»
   получает галочку, начинается строка «Составляем тест» со спиннером.
3. Если LLM вернула невалидный JSON и бэкенд ретраит — деталь строки
   «Составляем тест» на секунду меняется (например, «уточняем ответ модели»),
   спиннер остаётся тем же.
4. Готово — приходит `result`, чек-лист исчезает, показывается тест как и
   сегодня.
5. Если файл превышает лимит размера или Polza.ai недоступна — вместо
   результата показывается тот же текст ошибки, что и сегодня (красный блок
   под формой); чек-лист скрывается вместе со спиннером.

## Out of scope

- Отдельный джоб-стор / polling-эндпоинт — не нужен, пока это один запрос на
  один браузерный таб (SSE в том же соединении достаточно).
- Heartbeat/keep-alive SSE-комментарии на случай простаивающего соединения во
  время долгого LLM-вызова — в MVP не добавляются; если в проде вылезет
  обрыв соединения на длинных генерациях, это отдельная задача.
- Более гранулярные "смысловые" этапы генерации (темы → вопросы → проверка) —
  потребовали бы реального разбиения `generate_quiz()` на несколько LLM-вызовов,
  сознательно не делаем.
- Отмена генерации пользователем (закрыть вкладку прервёт SSE-соединение и
  фоновую `asyncio.Task` никак не остановит — она доработает до конца впустую).
  Ничего не meняем в этой части, как и сегодня.
